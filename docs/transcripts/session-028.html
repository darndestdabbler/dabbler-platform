Session 28: Take DabblerPdf 1.3.0, and measure report text the way it is drawn

Run only once DabblerPdf 1.3.0 is listed on nuget.org (Sessions 13–18 of ../dabbler-pdf, then that repository's nuget-v1.3.0 tag; it was listed on 2026-11-12). If it is not, report the first step blocked and say so.

  1. Register.
  2. Set the DabblerPdf PackageVersion in Directory.Packages.props from 1.1.3 to 1.3.0, the one place the platform pins it. The step's checks: Directory.Packages.props names DabblerPdf at 1.3.0 and nowhere at 1.1.3; dotnet test tests/Dabbler.Reports.Blazor.Tests passes; then, after a Release build and tools/pack.ps1 -OutputDir pack-output -CleanOutput, the .nuspec inside the packed Dabbler.Reports.Core nupkg declares its DabblerPdf dependency at 1.3.0.
  3. A field's height is measured by OpenPdfTextMeasurer (src/Libs/Dabbler.Reports.Core/Layout/) and its text drawn by PdfPageRenderer through PdfStyleResolver (src/Libs/Dabbler.Reports.Export/), and the two disagree:
  • each has its own word wrap (WrapParagraph and WrapText), and both split on single spaces and rejoin with one, so a run of spaces is collapsed in every PDF report, the bug DabblerPdf 1.2.0 fixed in TextLayout.WrapText;
  • a style with no font size is measured at 12 pt and drawn at ReportMetadata.DefaultFontSize (10 by default);
  • a style with no font family is measured in Helvetica and drawn in the family ReportMetadata.DefaultFontFamily maps to.

Give both one internal font resolver in Dabbler.Reports.Core (style, then report metadata, then the Base 14 mapping), and have the measurer count lines with TextLayout.CountLines and the renderer draw the lines of TextLayout.WrapText; delete both private wraps. A word wider than the field is now broken at characters, where it used to overflow. Tests go in tests/Dabbler.Reports.Blazor.Tests, in files named after the classes they test (add InternalsVisibleTo for an internal type): a double space in a field survives into the PDF's Tj operand; for a style with no size and no family, and for one with both, the measurer's line count equals the number of lines the renderer draws; a style with no size is measured at the report's default size. The step's check: dotnet test tests/Dabbler.Reports.Blazor.Tests passes.

  1. DabblerReportPage (src/Libs/Dabbler.Reports.Blazor/DabblerReportPage.razor.cs) composes with textMeasurer: null, so CanGrow and CanShrink never act in the shipped page: long text is clipped instead of growing its band. Pass an OpenPdfTextMeasurer built from the report definition. Add a test to tests/Dabbler.Reports.Blazor.Tests/DabblerReportPageTests.cs that a CanGrow field with three lines of text composes taller than its designed height. The step's check: dotnet test tests/Dabbler.Reports.Blazor.Tests passes.
  2. Cross-provider verification.
  3. The unit and e2e suites once against the verified tree, recorded as the run of record.
  4. Close-out.

Non-goals: no use of PdfWriter.CompressContentStreams; no change to the HTML ReportViewer's own text layout; no font other than the Base 14 (Session 29's); no change to DabblerVersion or CHANGELOG.md; the tracked *.csproj.lscache files are left alone.

Why now (2026-11-12): the platform's packages should depend on the DabblerPdf that carries the fixes its consumers asked for, and NuGet resolves the lowest version a dependency allows. Taking it changes nothing in a report unless the platform wraps with it: its own wraps collapse spaces exactly as TRIMS reported, and measuring and drawing with different fonts, sizes and wraps is how a grown field clips or leaves a gap. Found while planning DabblerPdf's Sessions 14–18. Amended 2026-11-12: 1.3.0 was listed before this session ran, so it takes 1.3.0 directly instead of 1.2.0, and Session 29 no longer moves the pin.
