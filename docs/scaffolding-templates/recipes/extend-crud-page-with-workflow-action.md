# Recipe: Extend a Generated CRUD Page with a Workflow Action

This recipe walks through adding a non-CRUD domain action — "Send Onboarding Email" — to a `Supplier` detail page that was generated by `dabbler-crud-slice`. The action is **adjacent** to the CRUD slice: it operates on a single supplier row, fits naturally on the supplier detail page, and reuses the page's existing identity/auth context, but it is **not** Create/Read/Update/Delete.

## When This Recipe Applies

**Use this recipe for:** a small, well-defined domain operation that hangs off a single CRUD entity — "Send onboarding email," "Mark as preferred supplier," "Trigger reconciliation," "Export details to PDF," "Archive without deleting." These are adjacent actions that benefit from sharing the detail page's loaded record and auth context.

**Do NOT use this recipe for:** workflow-driven flows — multi-step business processes with status state machines, transition gates, multi-entity orchestration, or domain-specific commands that compose multiple operations (e.g., "Place order," "Issue refund," "Onboard new customer through three-stage approval"). Those are **hand-authored pages**, not extensions of a CRUD scaffold. The scaffolder's place is the supplier *catalog*; the place for workflow logic is a dedicated workflow page that may consume the catalog but is not generated from it. See [README.md → When To Use This Scaffolder](../README.md#when-to-use-this-scaffolder) for the boundary.

A useful heuristic: if your action would naturally read as a sentence ending in "this supplier" or "this row," it's a candidate for this recipe. If it would naturally read as "starting a process that involves multiple entities, multiple steps, and approval gates," it is not.

## What This Recipe Adds

For the example "Send Onboarding Email" action:

| Layer | What gets added |
|---|---|
| Domain action service | `ISupplierWorkflowService` interface + `SupplierWorkflowService` implementation in the API project |
| API endpoint | `POST /api/suppliers/{id}/send-onboarding-email` in `SuppliersController` |
| API client method | `SendOnboardingEmailAsync(int id)` on `SupplierApiClient` |
| DI registration | Single `AddScoped<ISupplierWorkflowService, SupplierWorkflowService>()` in `Api/Program.cs` |
| UI affordance | A button in the detail page's `CustomActions` slot |
| Detail page extension | A `SupplierDetail.razor.cs` partial class holding the new handler |

The generated `SupplierDetail.razor` file is **not touched**, except for adding one button line in the `<CustomActions>` slot.

## Step 1 — Author the Domain Action Service

In `src/Apps/AcmeCoffeeOnline.Api/Services/`, add:

**`ISupplierWorkflowService.cs`:**

```csharp
namespace AcmeCoffeeOnline.Api.Services;

public interface ISupplierWorkflowService
{
    Task SendOnboardingEmailAsync(int supplierId, CancellationToken cancellationToken = default);
}
```

**`SupplierWorkflowService.cs`:**

```csharp
using AcmeCoffeeOnline.Api.Data;
using Microsoft.EntityFrameworkCore;

namespace AcmeCoffeeOnline.Api.Services;

public class SupplierWorkflowService : ISupplierWorkflowService
{
    private readonly AcmeCoffeeDbContext _context;
    private readonly IEmailService _email;

    public SupplierWorkflowService(AcmeCoffeeDbContext context, IEmailService email)
    {
        _context = context;
        _email = email;
    }

    public async Task SendOnboardingEmailAsync(int supplierId, CancellationToken cancellationToken = default)
    {
        var supplier = await _context.Suppliers
            .FirstOrDefaultAsync(s => s.Id == supplierId, cancellationToken)
            ?? throw new InvalidOperationException($"Supplier {supplierId} not found.");

        await _email.SendAsync(
            to: supplier.ContactEmail!,
            subject: "Welcome to AcmeCoffeeOnline",
            body: $"Hello {supplier.Name}, your onboarding packet is attached…",
            cancellationToken);
    }
}
```

Note: `IEmailService` stands in for whatever email transport the platform provides; substitute the real abstraction. Keep the service narrow — one method per concrete domain action — so adding a second action later is additive, not a refactor.

## Step 2 — Register the Service in DI

In `src/Apps/AcmeCoffeeOnline.Api/Program.cs`, alongside the existing `ISupplierService` registration:

```csharp
builder.Services.AddScoped<ISupplierService, SupplierService>();
builder.Services.AddScoped<ISupplierWorkflowService, SupplierWorkflowService>();  // ← new
```

This is the **only** edit to `Program.cs`. Do not edit `Web/Program.cs`; the scaffolding extension already registers everything the Web tier needs.

## Step 3 — Add the API Endpoint

In `src/Apps/AcmeCoffeeOnline.Api/Controllers/SuppliersController.cs`, append a new action method (do not modify any generated CRUD method):

```csharp
[HttpPost("{id}/send-onboarding-email")]
[DabblerEndpointAuthorize("SendSupplierOnboardingEmail")]
public async Task<IActionResult> SendOnboardingEmail(
    int id,
    [FromServices] ISupplierWorkflowService workflow,
    CancellationToken cancellationToken)
{
    await workflow.SendOnboardingEmailAsync(id, cancellationToken);
    return NoContent();
}
```

Then register the endpoint policy in `Api/Program.cs` alongside the generated supplier endpoint policies:

```csharp
endpoints.Add("SendSupplierOnboardingEmail", "Send Supplier Onboarding Email",
    "POST", "/api/suppliers/{id}/send-onboarding-email");
```

This entry makes the action authorizable through the platform security dashboard the same way the generated CRUD endpoints are.

## Step 4 — Add the API Client Method

The `dabbler-crud-page` template generates the typed `HttpClient` wrapper at `src/Apps/MyApp.Web/Data/SupplierApiClient.cs` with namespace `MyApp.Web.Data`. **Extend it via partial class** rather than editing the generated file. Alongside the generated file, create `src/Apps/MyApp.Web/Data/SupplierApiClient.Workflow.cs`:

```csharp
namespace AcmeCoffeeOnline.Web.Data;

public partial class SupplierApiClient
{
    public async Task SendOnboardingEmailAsync(int id, CancellationToken cancellationToken = default)
    {
        var response = await _httpClient.PostAsync(
            $"api/suppliers/{id}/send-onboarding-email",
            content: null,
            cancellationToken);
        response.EnsureSuccessStatusCode();
    }
}
```

Namespace and path must match the generated client. The template's file map (see [crud-page-template.md](../crud-page-template.md) → *File Map*) places the API client under `Data/` with namespace `<WebRoot>.Data`; the partial-class extension file lives next to it with the same namespace.

If `SupplierApiClient` is not currently declared `partial` in the generated file, add the `partial` modifier to it — this is the one allowed edit to the generated client. (A future template revision will emit `partial` by default.) The extension file is yours to own; the generated file remains regeneration-safe.

## Step 5 — Add the Button in the Detail Page's `CustomActions` Slot

In `src/Apps/AcmeCoffeeOnline.Web/Components/Pages/Suppliers/SupplierDetail.razor`, inside the existing `<CustomActions>` block, add one button:

```razor
<CustomActions>
    @if (!IsNew)
    {
        @* ── existing Undo + Delete buttons ── *@

        @* ── new: workflow-adjacent action ── *@
        <MudButton Variant="Variant.Outlined"
                   Color="Color.Secondary"
                   StartIcon="@Icons.Material.Filled.Email"
                   OnClick="HandleSendOnboardingEmailAsync"
                   Disabled="@(_session?.IsDirty == true || _saving)"
                   data-testid="send-onboarding-email-button">
            Send Onboarding Email
        </MudButton>
    }
</CustomActions>
```

The `Disabled` rule is important: workflow actions should not fire while the form has unsaved changes (the user might think the action operates on their pending edits). Disabling on `IsDirty == true` enforces "save or undo first."

This is the **only** edit to the generated `.razor` file. Everything else lives in the partial class below.

## Step 6 — Author the Handler in a Partial Class

Create `src/Apps/AcmeCoffeeOnline.Web/Components/Pages/Suppliers/SupplierDetail.razor.cs`:

```csharp
using MudBlazor;

namespace AcmeCoffeeOnline.Web.Components.Pages.Suppliers;

public partial class SupplierDetail
{
    private async Task HandleSendOnboardingEmailAsync()
    {
        if (_record is null) return;

        var confirmed = await DialogService.ShowMessageBox(
            "Send onboarding email?",
            $"This will email {_record.Name} at {_record.ContactEmail}.",
            yesText: "Send",
            cancelText: "Cancel");

        if (confirmed != true) return;

        try
        {
            _saving = true;
            await ApiClient.SendOnboardingEmailAsync(_record.Id);
            Snackbar.Add($"Onboarding email sent to {_record.Name}.", Severity.Success);
        }
        catch (Exception ex)
        {
            Snackbar.Add($"Failed to send onboarding email: {ex.Message}", Severity.Error);
        }
        finally
        {
            _saving = false;
            StateHasChanged();
        }
    }
}
```

The partial class lets you own the handler without modifying the regeneration-safe `.razor` file. If the page is ever re-scaffolded (e.g., to pick up a new generator improvement), the partial class survives untouched.

If the page currently does not declare `@code { … }` as a partial class, add `@code-behind` (Blazor partial-class style) by ensuring the `.razor` file's `@code` block compiles into the same partial class as the `.razor.cs` file. The standard Blazor convention does this automatically when both files share a class name and namespace.

## Step 7 — Tests

Add at minimum:

- **A bUnit test** on `SupplierDetail` that renders the page in a non-new state, clicks the "Send Onboarding Email" button, and asserts that `SupplierApiClient.SendOnboardingEmailAsync` was invoked exactly once with the expected supplier id. Mock the `SupplierApiClient` via the standard test DI override.
- **An integration test** on `SuppliersController.SendOnboardingEmail` that posts to the new endpoint and asserts the underlying `ISupplierWorkflowService.SendOnboardingEmailAsync` was called.

Playwright coverage for the action is recommended once a Playwright suite exists for the Supplier slice (which is deferred per the parent set's spec).

## What This Recipe Does NOT Do

This recipe deliberately does not:

- **Mutate the generated `.razor` markup beyond a single `<CustomActions>` button.** All logic lives in partial-class C# files.
- **Edit the generated `SupplierApiClient.cs`.** Workflow methods go in a separate partial-class file.
- **Touch the generated `Web/Program.cs` scaffolding extension call.** The wrapper-generated `AddSupplierScaffolding(builder.Configuration)` remains the single integration point on the Web side.
- **Introduce a workflow state machine.** This is one button doing one operation. If the action grows into a multi-step process with state transitions, that is the signal that you have outgrown this recipe and should author a dedicated workflow page instead.

## Generalizing the Pattern

For any new adjacent action on a generated CRUD page:

1. One narrow service interface + implementation in the API project.
2. One DI registration (one line in `Api/Program.cs`).
3. One controller method on the existing controller; one endpoint-policy registration.
4. One API-client partial-class method on the Web side.
5. One button in `<CustomActions>`; one handler in the page's `.razor.cs` partial class.

If a proposed action does not fit this five-touchpoint shape — for example, it needs to span multiple entities, drive a multi-page flow, or persist a multi-row state machine — it is a workflow, not a workflow-adjacent action, and belongs in a hand-authored page.
