## Decision 1: Unified Request DTO

**Chosen:** New `GridQueryRequest` type in `Dabbler.Api.Querying` (packable platform library; promoted from `AcmeCoffeeOnline.Shared.DTOs` during Session 2).

### Rationale

The existing `PagedRequest` in `AcmeCoffeeOnline.Shared.DTOs` is anemic for QBE queries: it supports only a single `SortBy` string and a free-text `SearchTerm`. It cannot represent the nested AND/OR filter graphs that `DeclarativeFilterPanel` emits via `CompositeFilterDescriptor`. Extending `PagedRequest` in-place risks backward compatibility with the existing Products, Customers, and Orders endpoints.

`GridDataRequest` (the UI contract from `Dabbler.Components.Data`) cannot be referenced from the API project — `Dabbler.Components` is a `Sdk.Razor` project with a MudBlazor dependency, which is inappropriate for a REST API.

**Session 1 chose:** thin transport types in `AcmeCoffeeOnline.Shared.DTOs`.
**Session 2 promoted to:** `Dabbler.Api.Querying` so scaffolded consumers can reference them as a NuGet package. The package has no MudBlazor / Razor dependency — only `Microsoft.EntityFrameworkCore` for the matching helper (kept in the same package to avoid an over-split).

### Types added

| Type | Description |
|---|---|
| `GridQueryRequest` | Root transport DTO: PageIndex, PageSize, Sorts, Filter |
| `GridQuerySort` | Record(PropertyName, Descending) |
| `GridQueryFilter` | Record(PropertyName, Operator string, Value?) — operator strings match `FilterOperators` constants |
| `GridCompositeFilter` | Recursive: Logic (And/Or), Filters[], Children[] |
| `GridFilterLogic` | Enum: And, Or |

**File:** `src/Libs/Dabbler.Api.Querying/GridQueryRequest.cs` (namespace `Dabbler.Api.Querying`).

### Mapping in the generated `GridDataProvider`

The generated `{Entity}GridDataProvider.cs` (Session 3) bridges the two type systems:
- Input: `Dabbler.Components.Data.GridDataRequest` from `IGridDataProvider<TDto>.FetchAsync`
- Output: posts `Dabbler.Api.Querying.GridQueryRequest` to the API via typed `HttpClient`

Mapping is mechanical: `Sorts` → `GridQuerySort[]` (1:1), `CompositeFilter` → `GridCompositeFilter` (recursive structural copy). `Groups` are not transported (server-side grouping is not in MVP scope).

Both sides reference `Dabbler.Api.Querying` (no leakage of consumer-app types into the scaffold).

### Response DTO

**Session 1 chose:** reuse the existing `PagedResponse<T>` from `AcmeCoffeeOnline.Shared.DTOs`.
**Session 2 superseded:** introduced `Dabbler.Api.Querying.GridQueryResponse<T>` so the scaffolded slice does not depend on consumer-app DTO shapes. The new type mirrors `PagedResponse<T>` in spirit (Items, TotalCount, paging metadata) but exposes `PageIndex` (zero-based, matching `GridQueryRequest.PageIndex`) instead of `Page` (one-based) — this aligns request and response paging conventions. Existing `AcmeCoffeeOnline.Shared.DTOs.PagedResponse<T>` is unchanged and continues to back the pre-scaffold endpoints (Customers / Products / Orders).

## Decision 2: HTTP Transport for `GridCompositeFilter`

**Chosen:** `POST /api/{entity}s/query` with `[FromBody] GridQueryRequest`

### Rationale

`GridCompositeFilter` is a recursive object graph (nested Children list). URL query strings cannot represent nested/recursive structures reliably — all common serialization approaches (JSON-encoded query param, multi-value params for nested objects) break with deep nesting, special characters, and max URL length constraints.

POST with a JSON body is the standard industry pattern for complex query documents ("search APIs"). It is stateless, cacheable at the application layer, and avoids all query-string limitations.

### Controller shape (generated by Session 2 template)

```csharp
[HttpPost("query")]
[DabblerEndpointAuthorize("Query{AuthPolicyPrefix}")]
public async Task<ActionResult<GridQueryResponse<{Entity}Dto>>> QueryAsync(
    [FromBody] GridQueryRequest request,
    CancellationToken cancellationToken)
{
    var response = await _service.QueryAsync(request, cancellationToken);
    return Ok(response);
}
```

`{AuthPolicyPrefix}` is derived by the template's `effectiveAuthPolicyPrefix` coalesce generator: it equals `--auth-policy-prefix` when provided, otherwise falls back to the `--entity` value. So a default invocation with `--entity Supplier` yields `QuerySupplier`, while `--entity Supplier --auth-policy-prefix BackofficeSupplier` yields `QueryBackofficeSupplier`. Field-permission application and per-user audit hooks belong to the consumer; the generated controller is intentionally thin.

### Coexistence with existing endpoints

Existing `ProductsController`, `CustomersController`, and `OrdersController` retain their `GET /api/{entity}s [FromQuery] PagedRequest` endpoints unchanged. Scaffolded controllers add a new `POST /api/{entity}s/query` endpoint alongside standard CRUD. No migration of existing endpoints is required.

## Decision 3: QBE → LINQ Helper Placement

**Chosen:** `Dabbler.Api.Querying.QueryableExtensions` (public static class in the new packable library; promoted from `AcmeCoffeeOnline.Api.Infrastructure` during Session 2).

### Rationale

The expression-tree builder translates `GridCompositeFilter` to `IQueryable<T>` predicates using BCL `System.Linq.Expressions`. The EF Core LINQ provider translates those expressions to SQL. The builder needs no EF Core-specific API — only `System.Linq.Expressions` — but lives in the same packable library as the transport DTOs so scaffolded consumers can install one NuGet package and get both halves of the contract.

See `qbe-helper-api.md` for the exact method signatures.
