## Known Limitations

### Not Validated In This Session

The following consumer scenarios are deferred to **Session 10 (Playwright E2E)**
and will be proven before the Session 11 human UAT handoff:

| Scenario | Reason deferred |
|---|---|
| Sign-in via magic link as `admin@local.test` | Requires a running app docker stack |
| Sample report renders + PDF export produces bytes | Requires a running app docker stack |
| `/admin/security` dashboard is reachable | Requires a running app docker stack |

### Binary Compatibility Caveat (Preview → 1.0)

The `Dabbler.Platform.Stubs` sub-package split (A3) moved types between assemblies
while preserving the namespace `Dabbler.Platform.Stubs`. This is **source compatible**
(existing `using` directives and code compile without changes) but **not binary
compatible** (already-compiled binaries referencing the old assembly location will
break without a rebuild).

For 0.1.0-preview.x: **a consumer rebuild is required after upgrading** between
preview versions if the assembly layout changed. Type forwarders are deferred to
a stable 1.0 release.

### Template Defaults Are Local-Feed Only

The scaffolded app's `DabblerApp.csproj` references `Dabbler.* 0.1.0-preview.1`
which does not exist on nuget.org. A consumer running `dotnet restore` after
scaffolding must configure a feed that contains these packages. The local pack
feed (`pack-output/`) generated by `tools/pack.ps1` serves this role in the
smoke tests. Once the packages are published to NuGet.org, this limitation is lifted.

Until publication: consumers must either:
- Clone the repo and use integrated source (existing `src/Libs/` path) per the
  primary project guidance, OR
- Run `tools/pack.ps1` locally and point NuGet at the resulting `pack-output/`
  directory

## Next Steps For External Consumers

1. **Publish packages.** Run `tools/pack.ps1`. Verify all 14 package IDs are
   present using `PackagingSmokeTests.PackOutput_ContainsAllRequiredLibraryNupkgs`,
   and verify the 12 library packages pass `Dabbler.PublicSurface.Tests`
   (README, icon, license, repository metadata, THIRD-PARTY-NOTICES where required).
   Then publish per `docs/packaging/release-checklist.md`.
2. **Install the template.** `dotnet new install Dabbler.Templates`.
3. **Scaffold.** `dotnet new dabbler-app -o MyApp --name MyApp` or
   `dotnet new dabbler-min -o MyApp --name MyApp`.
4. **Configure SQL Server.** Update `appsettings.json` `DefaultConnection` to your
   SQL Server instance.
5. **Start MailHog.** Needed for magic-link email delivery in development.
6. **Run.** `dotnet run` from the scaffolded project dir; sign in as
   `admin@local.test`.

See `docs/getting-started.md` for the full walkthrough.
